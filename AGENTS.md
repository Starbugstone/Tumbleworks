# Tumbleworks development reference

## Player experience priorities

For UX/UI updates, discuss the proposed behavior and layout with Claude Opus 5.5
at high effort, resolve objections, then implement the agreed decision.

**Graphics speed, fluid motion and player usability are the top priorities.**
Judge implementation and cleanup decisions by their effect on the player’s
modern upright phone, with about 375×690 CSS px available. Keep taps responsive,
animation continuous during successive actions, container patterns readable and
controls easy to reach. Maintainable code must support these outcomes.

Profile before changing rendering or simulation hot paths, compare against a
recorded baseline and keep the frame-time and download budgets passing. Verify
motion and real touch input in the running game; unit tests alone cannot prove
smoothness or usability. Browser measurements do not establish physical-phone
performance. Do not trade these priorities away for an abstraction, a cosmetic
cleanup or an unmeasured optimization.

**Hard rule: no unintended 3D clipping.** The marble must follow the actual
track and the surfaces of its moving cups, levers and lifts. Its swept volume
must clear solid walls, supports, other track sections, scenery and earned
village additions. Round bends and join their surface frames continuously;
never leave crossing rails, overlapping channel walls, spikes or a decorative
mechanism beneath a bypass ramp. Intentional contacts and connected joints
must be explicit in the geometry checks. Keep a failing regression for each
reported collision, and inspect the complete motion at the upright phone
viewport before calling the visual change finished. A clear path centre alone
does not establish clearance for the marble or the track's full width.
Exposed faces must not overlap in the same plane: trim, panes and mechanism
floors need real surface separation or a single shared surface, including at
moving handoffs. Keep coplanar-overlap regressions; renderer depth settings must
not conceal defective geometry.

**Village film camera:** follow the marble with smooth, eased travelling. Use at
most two gentle zoom-in excursions per film, reserved for major dramatic action;
do not refit the camera distance at each mechanism. Repeated zoom/dezoom makes the
player nauseous. The owner found the first films heavy and slow for a marble run:
keep the brisk pacing constants at the top of `src/world/village-cinematic.ts`. Preserve still-camera reduced-motion playback. The
`tumbleworks-film-camera` skill records the direction and verification workflow.

For village creation and village-machine repairs, use the project-local
[tumbleworks-village-authoring skill](.agents/skills/tumbleworks-village-authoring/SKILL.md).
It contains the current source/tool map, authoring rules, focused test runner and
end-to-end acceptance workflow. Codex discovers it under `.agents/skills/`;
Claude Code uses the linked `.claude/skills/tumbleworks-village-authoring/` entry.
Both paths share one copy.

## Default development workflow

Follow [the game development workflow](docs/development-workflow.md) for changes. The difficulty curve, its gates and the scoring tools are in [docs/levelling.md](docs/levelling.md).
Use the stages relevant to the task; a documentation edit needs content and link
checks, while gameplay changes need proof through the real machine and input.

- Define the player-visible result and a check that can fail before implementing.
- When fixing a recurring mistake or protecting a permanent rule, add the smallest
  useful lint rule, type constraint or regression check. Demonstrate that it rejects
  the failure and accepts valid behavior; prefer behavioral checks over source-text matching.
- Reproduce simulation bugs from a replay log (the level picker copies one; `scripts/replay.ts` plays it), and keep it as the regression. Rules code must stay replayable: no randomness, clocks, browser access or engine-dependent maths such as `Math.sin` (use `src/engine/exact-math.ts`), enforced by `npm run lint`.
- For consequential state transitions, write the invariant and check relevant
  interleavings. Major state machines get a checked model in `docs/models/`; update it
  with the transitions it covers, and replay counterexamples against the implementation
  before calling them game bugs.
- Profile before optimizing frame or tick code. `tests/e2e/performance.spec.ts` and the
  first-download budget in `npm run build` must keep passing; raise a ceiling only with a
  recorded baseline. Browser measurements are not phone measurements. Report checks actually run.

## Supported devices

**Hard rule: we only develop for modern phones held upright.** Landscape phones and small phones about 320 px wide are not supported. Do not design for them, spend code or screen space on them, test them, or weigh any decision against them. The reference is the player's phone: about 375x690 CSS px with the browser's bars showing.

## Permanent game names

Use these exact names in the interface, documentation and development discussions. Keep the internal kind and level IDs stable so existing progress continues to load.

`docs/research/` holds the reference research on the inspiring games. This reference and the current registered campaign define the implemented POC.

| **Funnel Sort** | `conveyor` / `board-*` (`PLAY_ORDER.conveyor`) | The Marble Sort style game. Tap a crate of nine marbles; they fall with physics into a clear funnel and pile there. The neck takes one marble at a time onto a belt that never stops, while the belt has room; the rest wait in the pile. Every dock has its own visible queue of three-slot boxes; the front box takes its colour as it passes, then the queue scrolls up. A full belt that cannot drain is a dead end. Later boards mix short trays of six with full trays of nine. Campaign lessons `board-200` and `board-201` at rounds 41 and 57 add paired release and forked shelves. Sealed-dock lesson `board-202` remains in the bank for round 73. `pairs` holds disjoint pairs of stable crate IDs (zero-based original supply/packet order); either endpoint atomically releases both only if both are accessible and unreleased, with pending packets ordered by ID and normal physical mixing. One undo restores both and the physics snapshot. `predecessors` replaces column access with an acyclic graph: at most three distinct predecessors per crate; all predecessors need accepted releases, never animation completion; expose at most four crates. Hints return crate IDs. The shared handle is a dark arch with a gold grip across the gap between its crates, posts beside their patterns. On paired boards a tap anywhere on a column pours its front crate, as on column boards (`columnTap` in `src/sim/shelf-marks.ts`), so a raised back crate is never a silent trap. Each crate that cannot be tipped yet carries a slate padlock beside its pattern, with one dark strap to every crate still in its way (`shelfMarks` in `src/sim/shelf-marks.ts`, from accepted rule state only): a strap goes the moment its blocker's release is accepted, the padlock pops when the last one goes, and a refused tap shakes the padlock and flashes its straps, without words. The player read the old grey rods and the raised back shelf as a stack whose top comes off first; front crates are never called supports. `seals` names a dock and a prerequisite `after: {dock, box}` at another dock (at most two, acyclic). A slate lid with a padlock covers the sealed dock's front box, inset so the box's own colour still shows, and bears the prerequisite box's pattern; a matching key tab sits on that box. The dock reserves nothing until the last prerequisite reservation opens it permanently, in the same transition before loss evaluation. | **Loop Sort** | `loop` / `loop-*` (`PLAY_ORDER.loop`) | The truck game: tube sorting on a ring. Trucks park in bays facing the loop; each bed holds colour segments packed against the cab. A truck takes its loop-end colour automatically as it passes the mouth. Tap a truck to pour its loop-end segment onto the loop and reach the segment behind it; a one-colour truck cannot be poured. A truck full of one colour clears the line and the next truck in the bay rolls up. Campaign lessons `loop-200` and `loop-95` at rounds 43 and 59 add receiving latches and short trucks. Older short-truck fixture `loop-201` and coupled-unload lesson `loop-202` (round 75) remain in the bank. `pourAfter` names a stable truck ID (explicit `id`, otherwise its original `lane:index`); dependencies must be acyclic. A latched truck still receives and may finish, but cannot pour until its prerequisite completes; completion opens every dependent latch before jam evaluation, without waiting for animation. A padlock on the tailboard and card carries the prerequisite’s finishing pattern; the card also prints the prerequisite lane number, and refused-tap feedback names and rings that lane, so same-colour cabs are unambiguous. Individual `capacity` overrides the board default: short beds hold 12 among beds of 24, with unchanged cabs, badges and touch floors, and percentages use each truck’s own capacity. Every colour’s total equals the sum of capacities of its finishing trucks. `couplings` contains disjoint pairs of stable IDs: tapping either atomically pours both open-end segments only when both are docked, unlatched, idle and have at least two segments. A failed pair changes nothing; a single undo restores both. When either completes, the link disappears in that same rules transition and the survivor taps normally. The coupling bar joins only docked tailboards; never show waiting toy trucks to complete it. It is dark with a light centre stripe, so it reads on the ivory beds and across the lane gap in grayscale; each linked card carries a dark link chip with the partner's lane number, and a refused tap on either truck names what holds the pair (still pouring, a latch, a one-colour partner, or a partner not yet docked). Searches use `LoopRules.actions()` and keys retain capacities, identities, latches and links. A full undrainable loop is still jammed: a latch does not block intake, and a hypothetical future unlock cannot rescue a state with no possible progress. The deepest segment fixes a truck's final colour, shown permanently by the cab paint and roof pattern. Moving tailboard chevrons indicate unloading; a pause symbol indicates that the full loop is holding the pour. The toy shows only each lane's docked truck, in one row with its open end at the top, against the belt: on an oval the ring goes round the row, on a figure-eight the belt lies on its side above it. Mouths must open on an oval's back straight, whose travel meets lanes in lane order, because the rule model takes marbles in that order; opening them on the front straight lost `loop-19`'s witness and stalled `loop-13`'s jam. Trucks are never drawn on the toy while they wait: the player took waiting trucks there for ones they could tap. Toy trucks carry patterns and no numbers. Numbers and the queue live in the lorry cards under the toy (`src/view/loop-roster.ts`; beside it on wide screens): one row per lane, numbered to match a pin on the toy, each truck a card with its cab on the left in its finishing colour and pattern, then its stretches in packing order with the open end at the right. The docked truck's card is raised and ivory, and is a tap target like the toy truck; waiting cards are flat and dark, and a tap on one plays the blocked sound and rings the docked truck, without pouring. When a truck leaves, the next card slides into its place. Each stretch has its own pattern and whole percentage, printed once; repeats of a colour are never summed, because the next pour is the stretch at the open end. Free room is a dashed empty stretch with its percentage, absent when the bed is full. The player found words here too much: the cards print numbers only. Colours sit on a dark rail, because yellow and orange nearly vanish on ivory. A stretch is never drawn narrower than its number needs, so short ones look a little longer than their true share; the number is the exact figure. Later levels will have more trucks, so all card and toy sizes come from one pure function, `rosterLayout` in `src/loop/roster-layout.ts`, with no per-level cases. It gives way in this order: toy height down to its floor, then row height, then the trucks furthest back fold into a `+n` tile that shows them on one tap. The docked truck and the next one always keep their numbers. `tests/loop/roster-layout.test.ts` runs it on every board and on invented larger ones, and `tests/e2e/loop.spec.ts` measures real numbers on all registered levels at the player's phone, about 375x690. The loop has a capacity; a full loop nobody can take from is a dead end, and so is a loop nobody can take from when no front truck has anything left to pour (the marbles it needs sit in a truck queued behind it): both are declared jammed. Rules count units. The loop is divided into capacity slots that travel with it, and each unit is drawn as rows of three tiny marbles filling its slot, so a full loop looks full. | `src/loop/` (rules, hint search, boards, layout, machine), `src/view/loop-scene.ts`, `src/gameplays/loop.ts` |
| **Tube Sort** | `tube` / `tube-*` (`PLAY_ORDER.tube`) | Move a contiguous matching group from the top of one tube into an empty tube or onto the same colour. Transfer as many as fit in one action. A home sized for one colour (`colorCapacities`) carries that colour's pattern on a plaque above its rail (`homePlaques` in `src/puzzles/home-plaques.ts`); a short tube filled with that colour does not count and makes the plaque pulse, without sound or words. `tube-210`'s spare opens on its own move and its cup folds on a later one: no reachable move does both. | `src/gameplays/tube.ts`, tube sections of `src/puzzles/`, `src/view/tubes.ts` |

“Drop game”, “belt game” and “Marble Sort style” mean Funnel Sort. “Truck game” means Loop Sort. Tray Match and Connected Match have been retired at the player’s request. Keep their saved IDs harmless; do not restore them to the campaign.

Reference material: Voodoo's Marble Sort! (funnel, belt, box columns) and Loop Sort (trucks on a loop). The feel targets taken from them: many marbles on screen, continuous motion, a tap that pays off within a tenth of a second, bulk resolution when a box or truck completes, and almost no interface over the toy.

## Campaign and shared engine

- The registered campaign currently has 60 rounds, 180 levels, interleaved by round (Funnel Sort, Loop Sort, Tube Sort). The target is 120 rounds, 360 levels; rounds 61–120 are not registered yet. `PLAY_ORDER` in `src/campaign.ts` lists what is registered, by stable ID; IDs imply nothing about order and saves are keyed by ID. The difficulty curve, its gates and how levels are authored, scored and assembled are in [docs/levelling.md](docs/levelling.md); the registry test follows `PLAY_ORDER`'s length. Older definitions stay in their banks with their IDs until the owner confirms a retirement. New rules (Funnel Sort paired release, forked shelves, sealed dock; Loop Sort latch, short trucks, coupled unload; Tube Sort capped spare, closing cup) have lesson boards in the banks from ID 200, playable in development at `/?try=<id>`. Rounds 41–60 register paired release, latches, the capped spare, forked shelves and short trucks, with follow-up practice; the other rules remain outside the campaign. Difficulty tiers are Getting started, Finding a rhythm, Thinking ahead and Full spectrum; `hasOrange` derives Full spectrum from a board's marble colours, not its position.
- In the registered campaign, orange first appears at Funnel Sort round 7 (`board-43`), Loop Sort round 7 (`loop-44`) and Tube Sort round 10 (`tube-44`). The older bank introductions were `tube-6`, `board-8` and `loop-8`; bank IDs are not campaign rounds. `FUNNEL_RECIPES` in `scripts/funnel-author.ts` covers boards 3–30; `LOOP_RECIPES` in `scripts/loop-author.ts` covers levels 6–30; `TUBE_RECIPES` in `scripts/tube-author.ts` covers levels 2–30. Earlier levels stay hand-authored and keep their guides. Tube Sort ramps gently; Funnel Sort boards 3–11 and Loop Sort levels 6–11 are re-rolled for tighter capacity and a minority of winning orders.
- Accept generated Funnel Sort and Loop Sort boards only after exhaustive memoised search over settled rule states finds a winning witness and a losing order, the winning share of complete orders falls inside the recipe's `win` band, and the opening in-game hint answers within 250 ms. Lower winning shares mean harder boards. Tighten capacity to the smallest solvable value plus recipe `slack`, capped at the recipe maximum: Funnel Sort's floor is `MIN_CAPACITY` for the track shape (oval 14, eight 26, wide eight 30), the smallest tracks that still draw cleanly; eights stay hard through fewer docks rather than a shorter belt; Loop Sort's floor is 20, with room above its starting load and default slack 4. Column-by-column, round-robin and reverse column-by-column pours must jam for Funnel Sort; lane-by-lane and round-robin taps must jam for Loop Sort. Every emitted witness must also win in the real machine (physics `Machine` with a brisk player for Funnel Sort, scripted `LoopMachine` within the test time limit for Loop Sort), because the settled rule model ignores belt timing and where marbles are absorbed; the authors try several winning orders and keep the first that does. Keep their witness and jam orders in `tests/witnesses.ts`; the first two Loop Sort tutorials have no losing order. A Loop Sort truck must never list the same colour in adjacent segments: `LoopRules` rejects such boards, because a one-colour truck could otherwise be poured.
- Loop Sort generation works backwards from a solved board through mirrored legal moves, keeping the loop free of colours wanted by front trucks. Tube Sort recipes fix colours, capacity, empties, optional part-full `spread` and a shortest-solution move range; `solveTube` must find that solution within its default in-game budget and 250 ms. Keep Tube Sort solutions with their board definitions.
- Use registered `GameplayPack` factories and the `GameRuntime` contract. `App` handles campaign and HUD without branching on gameplay kind.
- Reuse `Stage`, `MarbleFactory`, `MarbleCrowd` (instanced marbles for the two conveyor games), `PhysicsService`, `BoardView` and `BoardPointer`. Add a new type without copying marble entities, renderer setup, physics initialization or pointer capture.
- Rendering stays cheap for phones that run hot (measurements in [docs/verification.md](docs/verification.md), under Rendering cost). Draw scenes through `Stage.draw`, which compiles a new scene's shaders, hidden effects included, before the first frame. Give see-through plastic that shows both sides `Glass` (`src/engine/glass.ts`), never a double-sided transparent material, which rebuilds shader parameters twice a frame. Share materials and pattern textures per colour, and merge parts that share a material. Only floors receive shadows, and only marbles have clearcoat. Every toy is lit by one studio environment built in code (`src/engine/studio.ts`): a softbox along the key light gives each marble a single clean highlight. Each scene aims its shadow map at its own board with `Stage.fitShadows`, keeping the one-tap lookup. A village's shadows are drawn once and kept (`createScene('village')`, refreshed by `Stage.refreshShadows` when construction changes): only fixed land, houses, track and supports cast, everything drawn with the village material receives, and the sea under each island is one unlit mesh (`src/view/village-sea.ts`). The canvas renders at up to 1.5 device pixels per CSS pixel (`Stage.PIXEL_RATIOS`); a phone that runs slow gives up the finishing pass first, then steps down to 1.25 and 1. The finishing pass (`src/engine/finish.ts`: depth blur from the scene's own mip chain, glow and vignette in one extra pass) runs only on hardware renderers, is the first thing `Stage.lowerQuality` gives up, and can be forced with `?fx=1` or `?fx=0`; the frame-budget specs run without it, and `scripts/fx-cost.mjs` measured it at 36–50% of a frozen busy frame in software rendering. A board that can rest reports `still` so the app stops drawing it. `tests/e2e/render-hygiene.spec.ts` holds these.
- Keep rule state authoritative and update it as soon as a legal action is accepted. Animation must allow the next legal action while earlier movement continues. Preserve actor identity and retarget from its current visible position. Undo must cancel presentation safely and restore the complete prior action.
- Funnel Sort uses physics for the fall out of the crate and for the pile in the funnel. The neck is a closed floor with a scripted single-file exit (the earliest pour first among the marbles resting on it), because a physical hole of one marble width arches. The neck reserves a marble's belt slot at the moment it picks it, for where the entry will be when the marble reaches the bottom of the chute, and marbles still in the chute hold their slots: that is what keeps riders single file with full spacing and stops a landing from sliding along the belt. The track is sized to the belt capacity (`conveyorTrack` in `src/machine/layout.ts`): capacity slots at `SLOT_PITCH` close the loop and marbles land only in those slots, so a full belt is visibly full with no gaps and free room in the rules always means a slot that comes round within a lap. Never give a board a capacity below its shape's `MIN_CAPACITY`. A taken slot at landing is counted as a `bounce` recovery and must stay 0. From the neck a clear chute runs straight to the belt entry (`entryDistanceFor` in `src/machine/layout.ts`); the dish sits high enough that the figure-eight bridge ramps pass under it, and on an eight the chute joins the lower pass just before it dives under the bridge, never beneath the deck. Belt transport and delivery are scripted and the belt keeps moving. Waiting marbles in the pile must be retained and included in undo, accounting and diagnostics; the hint search approximates the pile as first in, first out. Loop Sort is fully scripted. Crates, boxes and cargo blocks must display the matching pattern on the container where it remains visible when filled.
- Color accessibility is required by the player, who is colour-blind and found yellow and green too close. The palette keeps a luminance gap between every pair: yellow is the brightest chromatic colour; white is a separate, lighter neutral, and green is a deep teal. Marbles themselves are plain glossy spheres in their natural colour: the player rejected surface textures, large symbols and camera-facing badges on marbles. The pattern language lives on the containers instead: crates, boxes, cargo blocks, truck cabs, tube slot rails and hints use **red = ring, blue = diamond, green = triangle, yellow = star, orange = cross, black = three solid dots in a row, white = heart**, and the legend sits in the level picker. Orange sits halfway up in luminance between the dark three and yellow, so no two colours on one hue line share a brightness band. Never rely on hue alone for a container.
- Keep touch, mouse, keyboard, undo, restart, current-state hints and local completion working across types. Test cancelled/invalid drags and rapid successive moves.
- Keep the interface out of the way: one slim top row (level pill, counter, sound), five round buttons at the bottom in the order restart, undo, hint, ×3, ×5, so a miss from a held button never reloads the level. The written instruction toast shows only during onboarding, while a level's guide is unseen; the player could not stand it on every level. The level picker, title, difficulty and pattern legend live behind the level pill. The player asked for the toy to fill the screen.
- Fast forward is a hold, not a toggle: a button (pointer capture, any pointer) or a key (`f` for ×3, `g` for ×5) runs the simulation at `App.FAST_SPEED` or `App.FASTER_SPEED` ticks per frame while held; if both are held the faster wins, and lifting it falls back to the other. It runs through the same `advance()` path the tests use, and drops back to normal on release, blur, hidden tab, level change or when the level ends. Any pointer may hold it and a second finger can still tap the board. Rules never see the speed; only tick cadence changes. Small per-marble sounds rest while held. It exists for the waits when a full belt or loop needs a lap before anything can unload.
- Boards are calm: no floor grid, props, hazard studs, neon rails, printed text or numbers on the platform. The world around every board is a shallow sunlit lagoon (`ArcadeYard` in `src/view/arcade.ts`): one water plane whose light net drifts slowly and whose foam laps the hull, with low-poly islets outside the board. The water advances only on frames the board already draws, so a resting board still costs nothing, and it is frozen under reduced motion. Every toy body is `hull()` from the same file (ivory shell, gold step, plum deck, ivory rail), fused with that game's wells, trays and towers into one draw by vertex colour. The owner then judged the violet toy too close to the original and chose a premium-toy direction with its own style, free to reshape. The machine (`ARCADE` palette) is now a thick ivory lacquer shell with a gold step, a plum deck and near-black plum wells; plum is a hue no cargo colour uses. Every plastic takes the moulded shading in `src/engine/candy.ts` (light along rounded edges, deeper sides, and floor shading baked once per board from a top-down look at the body), and crates and boxes are two-tone (`moulded`). Tube bases stay plum, never ivory, because cargo is seen against them. The frame is light with dark wells: the belt channel, the dock wells, the Tube Sort deck and the tower behind Funnel Sort's crates are dark, so cargo is always read against dark plastic and never against the bright water or frame. The owner asked for a bold candy-toy look in a sunny miniature world, then for more active visuals during play. The owner rejected the large pattern symbol that popped off a finished piece, and asked for sparkle and for marbles that land with weight. Motion comes from what the player causes and stays at the piece. A crate swells once when it becomes the one to tap, a box hops once as it docks, and a finished box jumps. All sparkle is one pooled draw (`Sparks` in `src/engine/sparks.ts`): a few flecks where an accepted tap lands; a small glint and flecks where a marble seats, while the box dips under it; and for a finished box, lorry or tube a glow behind it, small twinkles and a slow cloud of fine dust in gold, white and its own colour (the owner found large stars too big and asked for fairy dust), growing over a streak of finishes within two seconds. A won level adds one fountain at each hull corner. Glitter dies before it falls back onto the piece below, and the finished piece keeps its own printed pattern, so nothing is told by hue alone. The owner then asked for an arcade feel: a poured lorry rocks on its wheels and kicks up dust as it leaves, marbles already in a box hop when another lands, the box flattens under its last marble and turns once in the air with its cargo, a marble quicker than the belt is drawn slightly long and leaves a short trail, and the win fountains fire in sequence, smaller if an undo or hint was used. Vibration was tried and removed: the owner's Android phone gave none. Camera shake is allowed only for the exceptional moment, in the owner's words: today that is the third finish of a streak (`Shake` in `src/engine/shake.ts`), never an ordinary finish. A light surface directly behind cargo stays ruled out, because yellow and orange vanish on it. Belt motion is shown by the belt itself (`src/view/belt-surface.ts`): one textured strip along the transport path whose low-contrast plates, seams and small chevrons scroll with `beltDistance`. Do not reintroduce tick bars or chasing markers across the channel; the player found them too heavy.
- The first three campaign levels teach their controls with small gently animated tap-hand icons over real targets, with the short instruction toast until the first tap, the guide ends or six seconds pass. Guides follow accepted rule state, can be skipped or restarted, and remember completion. Existing level completion must not hide an unseen guide. Respect reduced-motion settings. English and French can be switched without restarting a puzzle. Keep the permanent game names as brands in both languages.
- The first two Loop Sort levels start empty and fit all intended pours without a capacity stall. Keep congestion for later levels. The full 120-round target campaign must include figure-eight levels in both conveyor types and end each with two eights. The current partial campaign registers Funnel Sort eights `board-46`, `board-74`, `board-89` (a wide eight) and `board-91`, and no Loop Sort eights; Loop eights remain in the bank outside `PLAY_ORDER`. This is an outstanding assembly target, not current release coverage. Movement and the raised bridge must use the same per-machine path as the mesh.
- Frame mobile views around playable pieces rather than decorative bases, keeping touch targets and departures clear of the HUD.
- Keep ambient and perimeter lighting steady. The player rejected flashing or chasing side lights. Put motion and completion feedback at the active truck, crate or receiving box.
- Waiting Funnel Sort boxes are drawn larger than the machine's half size and show their pattern large on top until they dock, because the small front-wall badge could not be read at phone width. Funnel Sort boxes fill visually **left → right → middle**. The owner found arrivals too weak: each of the first two landings dips the box briefly and glints in its pocket, and the third, middle landing gives the box and its contents a brief shake and a rounded completion sound. Trigger this on capture, never the earlier slot reservation. Keep the next box usable during departure. The player rejected arrival rings, the Funnel Sort “LOADED!” stamp and Tube Sort “SORTED” labels. Reduced motion suppresses the shake and sparks; held fast forward keeps only the final landing sound. These presentation changes must preserve rule timing and replay state.
- Sound effects use the small CC0 Kenney bank documented in `assets/audio/README.md`. Preserve source licences and reproducible compression. Count compressed audio toward the download budget, including files loaded after a gesture, and keep the separate 45 KB audio ceiling. Decode each sample once without blocking input or replaying stale cues after loading. Keep impacts quiet and bounded, reserve voices for rewards, and cancel tails on mute, Undo, Restart, level change, blur and hidden tabs.

## Runtime and checks

The project uses TypeScript, Three.js and Rapier. Use the versions pinned in `package.json`. The development server runs through Docker Compose on port 5180 and is reachable by phones on the same LAN.

A push to `main` deploys to <https://tumbleworks.starbugstone.com> once `.github/workflows/ci.yml` passes on that commit; a cron job on o2switch pulls and builds it. See `docs/deployment.md`. `scripts/o2switch/` and the template's tests in `tests/o2switch/` are unchanged copies of `Starbugstone/test-auto-deploy`: fix them there first. `public/.htaccess` must keep its certificate-renewal rule and must not gain a fallback to `index.html`, because a removed bundle answered with HTML leaves a black page.

```sh
docker compose up --build
docker compose exec -T dev npm run typecheck
docker compose exec -T dev npm run lint                       # determinism rules for src/sim, src/machine, src/loop, src/puzzles
docker compose exec -T dev npm test
docker compose exec -T dev npm run build
docker compose --profile e2e run --rm e2e npx playwright test
docker compose --profile e2e run --rm e2e npx playwright test tests/e2e/performance.spec.ts --no-deps   # busiest levels at 4x CPU slowdown, alone; the full run plays them last
```
