# Tumbleworks development reference

## Default development workflow

Follow [the game development workflow](docs/development-workflow.md) for changes. The difficulty curve, its gates and the scoring tools are in [docs/levelling.md](docs/levelling.md).
Use the stages relevant to the task; a documentation edit needs content and link
checks, while gameplay changes need proof through the real machine and input.

- Define the player-visible result and a check that can fail before implementing.
- When fixing a recurring mistake or protecting a permanent rule, add the smallest
  useful lint rule, type constraint or regression check. Demonstrate that it rejects
  the failure and accepts valid behavior; prefer behavioral checks over source-text matching.
- Reproduce simulation bugs from a replay log (the level picker copies one; `scripts/replay.ts` plays it), and keep it as the regression. Rules code must stay replayable: no randomness, clocks, browser access or engine-dependent maths such as `Math.sin` (use `src/engine/exact-math.ts`), enforced by `npm run lint`.
- For consequential state transitions, write the invariant and check relevant
  interleavings. Major state machines get a checked model in `docs/models/`; update it
  with the transitions it covers, and replay counterexamples against the implementation
  before calling them game bugs.
- Profile before optimizing frame or tick code. `tests/e2e/performance.spec.ts` and the
  first-download budget in `npm run build` must keep passing; raise a ceiling only with a
  recorded baseline. Browser measurements are not phone measurements. Report checks actually run.

## Supported devices

**Hard rule: we only develop for modern phones held upright.** Landscape phones and small phones about 320 px wide are not supported. Do not design for them, spend code or screen space on them, test them, or weigh any decision against them. The reference is the player's phone: about 375x690 CSS px with the browser's bars showing.

## Permanent game names

Use these exact names in the interface, documentation and development discussions. Keep the internal kind and level IDs stable so existing progress continues to load.

`docs/research/` holds the reference research on the inspiring games. This reference and the current registered campaign define the implemented POC.

| Permanent name | Internal kind / level IDs | Meaning and rules | Implementation |
| --- | --- | --- | --- |
| **Funnel Sort** | `conveyor` / `board-1`…`board-30` | The Marble Sort style game. Tap a crate of nine marbles; they fall with physics into a clear funnel and pile there. The neck takes one marble at a time onto a belt that never stops, while the belt has room; the rest wait in the pile. Every dock has its own visible queue of three-slot boxes; the front box takes its colour as it passes, then the queue scrolls up. A full belt that cannot drain is a dead end. Later boards mix short trays of six with full trays of nine. Bank lessons `board-200`–`board-202` (outside `PLAY_ORDER`, rounds 41/57/73) add paired release, forked shelves and sealed docks. `pairs` holds disjoint pairs of stable crate IDs (zero-based original supply/packet order); either endpoint atomically releases both only if both are accessible and unreleased, with pending packets ordered by ID and normal physical mixing. One undo restores both and the physics snapshot. `predecessors` replaces column access with an acyclic graph: at most three distinct predecessors per crate; all predecessors need accepted releases, never animation completion; expose at most four crates. Hints return crate IDs. The shared handle sits on crates, and overlap/short brackets show shelf dependencies without slab arrows. `seals` names a dock and a prerequisite `after: {dock, box}` at another dock (at most two, acyclic). A shutter bears that box's colour/pattern; it reserves nothing until the last prerequisite reservation opens it permanently, in the same transition before loss evaluation. A full belt wanted only by sealed docks jams; hypothetical future unlocks do not rescue it. All searches and players use `MachineRules.actions()`/`release()`, key released IDs and seals, and enumerate variant capacities without assuming monotonicity. The neck arbitration, landing-slot reservation and zero-recovery requirement are unchanged. | `src/sim/` (rules, hint search, boards), `src/machine/`, `src/view/scene.ts`, `src/gameplays/conveyor.ts` |
| **Loop Sort** | `loop` / `loop-1`…`loop-30` | The truck game: tube sorting on a ring. Trucks park in bays facing the loop; each bed holds colour segments packed against the cab. A truck takes its loop-end colour automatically as it passes the mouth. Tap a truck to pour its loop-end segment onto the loop and reach the segment behind it; a one-colour truck cannot be poured. A truck full of one colour clears the line and the next truck in the bay rolls up. Rule lessons in the bank (`loop-200`–`loop-202`, outside `PLAY_ORDER`) add receiving latches, short trucks and coupled unloads for lesson rounds 43, 59 and 75. `pourAfter` names a stable truck ID (explicit `id`, otherwise its original `lane:index`); dependencies must be acyclic. A latched truck still receives and may finish, but cannot pour until its prerequisite completes; completion opens every dependent latch before jam evaluation, without waiting for animation. A padlock on the tailboard and card carries the prerequisite’s finishing pattern; the card also prints the prerequisite lane number, and refused-tap feedback names and rings that lane, so same-colour cabs are unambiguous. Individual `capacity` overrides the board default: short beds hold 12 among beds of 24, with unchanged cabs, badges and touch floors, and percentages use each truck’s own capacity. Every colour’s total equals the sum of capacities of its finishing trucks. `couplings` contains disjoint pairs of stable IDs: tapping either atomically pours both open-end segments only when both are docked, unlatched, idle and have at least two segments. A failed pair changes nothing; a single undo restores both. When either completes, the link disappears in that same rules transition and the survivor taps normally. The coupling bar joins only docked tailboards; never show waiting toy trucks to complete it. Searches use `LoopRules.actions()` and keys retain capacities, identities, latches and links. A full undrainable loop is still jammed: a latch does not block intake, and a hypothetical future unlock cannot rescue a state with no possible progress. The deepest segment fixes a truck's final colour, shown permanently by the cab paint and roof pattern. Moving tailboard chevrons indicate unloading; a pause symbol indicates that the full loop is holding the pour. The toy shows only each lane's docked truck, in one row with its open end at the top, against the belt: on an oval the ring goes round the row, on a figure-eight the belt lies on its side above it. Mouths must open on an oval's back straight, whose travel meets lanes in lane order, because the rule model takes marbles in that order; opening them on the front straight lost `loop-19`'s witness and stalled `loop-13`'s jam. Trucks are never drawn on the toy while they wait: the player took waiting trucks there for ones they could tap. Toy trucks carry patterns and no numbers. Numbers and the queue live in the lorry cards under the toy (`src/view/loop-roster.ts`; beside it on wide screens): one row per lane, numbered to match a pin on the toy, each truck a card with its cab on the left in its finishing colour and pattern, then its stretches in packing order with the open end at the right. The docked truck's card is raised and ivory, and is a tap target like the toy truck; waiting cards are flat and dark, and a tap on one plays the blocked sound and rings the docked truck, without pouring. When a truck leaves, the next card slides into its place. Each stretch has its own pattern and whole percentage, printed once; repeats of a colour are never summed, because the next pour is the stretch at the open end. Free room is a dashed empty stretch with its percentage, absent when the bed is full. The player found words here too much: the cards print numbers only. Colours sit on a dark rail, because yellow and orange nearly vanish on ivory. A stretch is never drawn narrower than its number needs, so short ones look a little longer than their true share; the number is the exact figure. Later levels will have more trucks, so all card and toy sizes come from one pure function, `rosterLayout` in `src/loop/roster-layout.ts`, with no per-level cases. It gives way in this order: toy height down to its floor, then row height, then the trucks furthest back fold into a `+n` tile that shows them on one tap. The docked truck and the next one always keep their numbers. `tests/loop/roster-layout.test.ts` runs it on every board and on invented larger ones, and `tests/e2e/loop.spec.ts` measures real numbers on all thirty levels at the player's phone, about 375x690. The loop has a capacity; a full loop nobody can take from is a dead end, and so is a loop nobody can take from when no front truck has anything left to pour (the marbles it needs sit in a truck queued behind it): both are declared jammed. Rules count units. The loop is divided into capacity slots that travel with it, and each unit is drawn as rows of three tiny marbles filling its slot, so a full loop looks full. | `src/loop/` (rules, hint search, boards, layout, machine), `src/view/loop-scene.ts`, `src/gameplays/loop.ts` |
| **Tube Sort** | `tube` / `tube-1`…`tube-30` | Move a contiguous matching group from the top of one tube into an empty tube or onto the same colour. Transfer as many as fit in one action. Support touch dragging and two-tap input. Sort full tubes of one type. | `src/gameplays/tube.ts`, tube sections of `src/puzzles/`, `src/view/tubes.ts` |

“Drop game”, “belt game” and “Marble Sort style” mean Funnel Sort. “Truck game” means Loop Sort. Tray Match and Connected Match have been retired at the player’s request. Keep their saved IDs harmless; do not restore them to the campaign.

Reference material: Voodoo's Marble Sort! (funnel, belt, box columns) and Loop Sort (trucks on a loop). The feel targets taken from them: many marbles on screen, continuous motion, a tap that pays off within a tenth of a second, bulk resolution when a box or truck completes, and almost no interface over the toy.

## Campaign and shared engine

- Funnel Sort, Loop Sort and Tube Sort each have thirty levels, for ninety levels total. The registry interleaves them by round (`board-n`, `loop-n`, `tube-n`) in `src/campaign.ts`, preserving the original seventeen's order and existing save IDs. The registry test expects all ninety IDs. Difficulty tiers are Getting started, Finding a rhythm, Thinking ahead and Full spectrum; `hasOrange` derives Full spectrum from a board's marble colours, not its position.
- The fifth colour, orange, arrives in Tube Sort's sixth level and then in the eighth Funnel Sort and Loop Sort levels. `FUNNEL_RECIPES` in `scripts/funnel-author.ts` covers boards 3–30; `LOOP_RECIPES` in `scripts/loop-author.ts` covers levels 6–30; `TUBE_RECIPES` in `scripts/tube-author.ts` covers levels 2–30. Earlier levels stay hand-authored and keep their guides. Tube Sort ramps gently; Funnel Sort boards 3–11 and Loop Sort levels 6–11 are re-rolled for tighter capacity and a minority of winning orders.
- Accept generated Funnel Sort and Loop Sort boards only after exhaustive memoised search over settled rule states finds a winning witness and a losing order, the winning share of complete orders falls inside the recipe's `win` band, and the opening in-game hint answers within 250 ms. Lower winning shares mean harder boards. Tighten capacity to the smallest solvable value plus recipe `slack`, capped at the recipe maximum: Funnel Sort's floor is `MIN_CAPACITY` for the track shape (oval 14, eight 26, wide eight 30), the smallest tracks that still draw cleanly; eights stay hard through fewer docks rather than a shorter belt; Loop Sort's floor is 20, with room above its starting load and default slack 4. Column-by-column, round-robin and reverse column-by-column pours must jam for Funnel Sort; lane-by-lane and round-robin taps must jam for Loop Sort. Every emitted witness must also win in the real machine (physics `Machine` with a brisk player for Funnel Sort, scripted `LoopMachine` within the test time limit for Loop Sort), because the settled rule model ignores belt timing and where marbles are absorbed; the authors try several winning orders and keep the first that does. Keep their witness and jam orders in `tests/witnesses.ts`; the first two Loop Sort tutorials have no losing order. A Loop Sort truck must never list the same colour in adjacent segments: `LoopRules` rejects such boards, because a one-colour truck could otherwise be poured.
- Loop Sort generation works backwards from a solved board through mirrored legal moves, keeping the loop free of colours wanted by front trucks. Tube Sort recipes fix colours, capacity, empties, optional part-full `spread` and a shortest-solution move range; `solveTube` must find that solution within its default in-game budget and 250 ms. Keep Tube Sort solutions with their board definitions.
- Use registered `GameplayPack` factories and the `GameRuntime` contract. `App` handles campaign and HUD without branching on gameplay kind.
- Reuse `Stage`, `MarbleFactory`, `MarbleCrowd` (instanced marbles for the two conveyor games), `PhysicsService`, `BoardView` and `BoardPointer`. Add a new type without copying marble entities, renderer setup, physics initialization or pointer capture.
- Keep rule state authoritative and update it as soon as a legal action is accepted. Animation must allow the next legal action while earlier movement continues. Preserve actor identity and retarget from its current visible position. Undo must cancel presentation safely and restore the complete prior action.
- Funnel Sort uses physics for the fall out of the crate and for the pile in the funnel. The neck is a closed floor with a scripted single-file exit (the earliest pour first among the marbles resting on it), because a physical hole of one marble width arches. The neck reserves a marble's belt slot at the moment it picks it, for where the entry will be when the marble reaches the bottom of the chute, and marbles still in the chute hold their slots: that is what keeps riders single file with full spacing and stops a landing from sliding along the belt. The track is sized to the belt capacity (`conveyorTrack` in `src/machine/layout.ts`): capacity slots at `SLOT_PITCH` close the loop and marbles land only in those slots, so a full belt is visibly full with no gaps and free room in the rules always means a slot that comes round within a lap. Never give a board a capacity below its shape's `MIN_CAPACITY`. A taken slot at landing is counted as a `bounce` recovery and must stay 0. From the neck a clear chute runs straight to the belt entry (`entryDistanceFor` in `src/machine/layout.ts`); the dish sits high enough that the figure-eight bridge ramps pass under it, and on an eight the chute joins the lower pass just before it dives under the bridge, never beneath the deck. Belt transport and delivery are scripted and the belt keeps moving. Waiting marbles in the pile must be retained and included in undo, accounting and diagnostics; the hint search approximates the pile as first in, first out. Loop Sort is fully scripted. Crates, boxes and cargo blocks must display the matching pattern on the container where it remains visible when filled.
- Color accessibility is required by the player, who is colour-blind and found yellow and green too close. The palette keeps a luminance gap between every pair: yellow is the brightest chromatic colour; white is a separate, lighter neutral, and green is a deep teal. Marbles themselves are plain glossy spheres in their natural colour: the player rejected surface textures, large symbols and camera-facing badges on marbles. The pattern language lives on the containers instead: crates, boxes, cargo blocks, truck cabs, tube slot rails and hints use **red = ring, blue = diamond, green = triangle, yellow = star, orange = cross, black = three solid dots in a row, white = heart**, and the legend sits in the level picker. Orange sits halfway up in luminance between the dark three and yellow, so no two colours on one hue line share a brightness band. Never rely on hue alone for a container.
- Keep touch, mouse, keyboard, undo, restart, current-state hints and local completion working across types. Test cancelled/invalid drags and rapid successive moves.
- Keep the interface out of the way: one slim top row (level pill, counter, sound), five round buttons at the bottom in the order restart, undo, hint, ×3, ×5, so a miss from a held button never reloads the level. The written instruction toast shows only during onboarding, while a level's guide is unseen; the player could not stand it on every level. The level picker, title, difficulty and pattern legend live behind the level pill. The player asked for the toy to fill the screen.
- Fast forward is a hold, not a toggle: a button (pointer capture, any pointer) or a key (`f` for ×3, `g` for ×5) runs the simulation at `App.FAST_SPEED` or `App.FASTER_SPEED` ticks per frame while held; if both are held the faster wins, and lifting it falls back to the other. It runs through the same `advance()` path the tests use, and drops back to normal on release, blur, hidden tab, level change or when the level ends. Any pointer may hold it and a second finger can still tap the board. Rules never see the speed; only tick cadence changes. Small per-marble sounds rest while held. It exists for the waits when a full belt or loop needs a lap before anything can unload.
- Boards are calm: no floor grid, props, hazard studs, neon rails, printed text or numbers on the platform. The ground is a soft pool of light under a teal slab. Belt motion is shown by the belt itself (`src/view/belt-surface.ts`): one textured strip along the transport path whose low-contrast plates, seams and small chevrons scroll with `beltDistance`. Do not reintroduce tick bars or chasing markers across the channel; the player found them too heavy.
- The first three campaign levels teach their controls with small gently animated tap-hand icons over real targets, with the short instruction toast until the first tap, the guide ends or six seconds pass. Guides follow accepted rule state, can be skipped or restarted, and remember completion. Existing level completion must not hide an unseen guide. Respect reduced-motion settings. English and French can be switched without restarting a puzzle. Keep the permanent game names as brands in both languages.
- The first two Loop Sort levels start empty and fit all intended pours without a capacity stall. Keep congestion for later levels. Each conveyor type includes figure-eight levels and ends with two of them; movement and the raised bridge must use the same per-machine path as the mesh.
- Frame mobile views around playable pieces rather than decorative bases, keeping touch targets and departures clear of the HUD.
- Keep ambient and perimeter lighting steady. The player rejected flashing or chasing side lights. Put motion and completion feedback at the active truck, crate or receiving box.

## Runtime and checks

The project uses TypeScript, Three.js and Rapier. Use the versions pinned in `package.json`. The development server runs through Docker Compose on port 5180 and is reachable by phones on the same LAN.

A push to `main` deploys to <https://tumbleworks.starbugstone.com> once `.github/workflows/ci.yml` passes on that commit; a cron job on o2switch pulls and builds it. See `docs/deployment.md`. `scripts/o2switch/` and the template's tests in `tests/o2switch/` are unchanged copies of `Starbugstone/test-auto-deploy`: fix them there first. `public/.htaccess` must keep its certificate-renewal rule and must not gain a fallback to `index.html`, because a removed bundle answered with HTML leaves a black page.

```sh
docker compose up --build
docker compose exec -T dev npm run typecheck
docker compose exec -T dev npm run lint                       # determinism rules for src/sim, src/machine, src/loop, src/puzzles
docker compose exec -T dev npm test
docker compose exec -T dev npm run build
docker compose --profile e2e run --rm e2e npx playwright test
docker compose --profile e2e run --rm e2e npx playwright test tests/e2e/performance.spec.ts   # busiest levels at 4x CPU slowdown; run it alone
docker compose exec -T dev npx tsx scripts/replay.ts <log.json>   # plays a game copied from the level picker and checks it reproduces
bash scripts/check-models.sh                                  # TLC in Docker: every model holds and every deliberate break is caught
bash tests/o2switch/site-test.sh                              # real hosting build, Apache rules and browser smoke; needs PHP, Node and Docker on the machine
docker compose exec -T dev npx tsx scripts/board-tree.ts      # Funnel Sort release trees, for authoring
docker compose exec -T dev npx tsx scripts/loop-tree.ts       # Loop Sort tap trees, for authoring
docker compose exec -T dev npx tsx scripts/machine-soak.ts    # physical Funnel Sort witnesses, recoveries must stay 0
docker compose exec -T dev npx tsx scripts/loop-soak.ts       # scripted Loop Sort witnesses
docker compose exec -T dev npx tsx scripts/funnel-author.ts stats [ids…]   # recipe metrics; omit IDs for all
docker compose exec -T dev npx tsx scripts/funnel-author.ts emit [ids…]    # board definitions, witnesses, jams and French titles
docker compose exec -T dev npx tsx scripts/loop-author.ts stats [ids…]     # recipe metrics; omit IDs for all
docker compose exec -T dev npx tsx scripts/loop-author.ts emit [ids…]      # board definitions, witnesses, jams and French titles
docker compose exec -T dev npx tsx scripts/tube-author.ts batch            # recipe boards with verified shortest solutions and French titles
docker compose exec -T dev npx tsx scripts/tube-author.ts 5 5 2 1 12 22   # random Tube Sort board: colours, capacity, empties, seed, move range; optional spread follows
docker compose --profile e2e run --rm e2e node scripts/peek.mjs <levelIndex>   # phone and desktop captures into output/current/peek
```

Keep authored winning witnesses and actual losing choices for each difficulty. Verify real browser input, modern phone layouts, the existing desktop layout and grayscale readability of colors and container patterns. Deterministic browser-clock tests prove behavior, not performance on a physical phone. Preserve pre-existing user processes and historical output artifacts: specs and capture scripts write to `output/current`, never into `output/poc9` or `output/poc12`.
